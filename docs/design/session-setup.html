UX design · training session settings

The session card reads its own permissions.

Five new endpoints let a runner reshape a planned session: terrain, effort, volume, shoe, and the session itself. This design puts all of it behind one row of chips that doubles as the status display — what is applied is what you tap to change.

The hard question was “which change is allowed on which workout?” It turns out we never have to answer it. GET /schedule/trainings/{id} ships can_change_distance, can_change_intensity, can_cross_train, can_be_exchanged and the matching change_*_package objects — steps, labels and coach copy included. The UI is a projection of that response. A tempo run that refuses a distance change simply arrives without the chip.

Identity strip

Colour comes from the server, not from us

hex_training is already per-workout-type — #E69F00 for tempo, #7B3294 for easy + strides, #1BB9AA for cycling — and it is the same value the mobile app paints. We use it for the 3 px rail and an 18% tint behind the activity icon, never as text colour: several of those hues fail contrast on the charcoal ground.

Identity strip

The icon says the activity, the bar says the shape

One icon per activity (run, bike) is safe to derive from cross_type. A second icon set for workout type would not be: titles are localised and the list is open-ended. Instead the 6 px shape bar draws the blocks — a solid slab is a tempo, a comb of thin marks is intervals or strides. It costs one line and reads before the title does.

Chip rail

The badge is the button

Every chip is both the applied value and the way in. Chips that still match the coach’s plan sit muted; anything you changed picks up a pink dot and a tinted border, so “what did I touch on this session” is one glance. Effort and volume chips only appear once they differ from plan — at 0% they are noise.

Chip rail

One trailing control, not a toolbar

The sliders chip is the only always-present affordance and the only way to reach a setting that has no chip yet. The header keeps its existing icons for session-level actions — treadmill, move, delete — so setup lives in exactly one place.

Sheet

Two levels, one screen deep

A chip opens the sheet directly on its editor; the sliders chip opens the index and you drill in once. A pick commits and closes — shoe, activity. A dial commits and stays, because the whole point of moving the effort step is watching the total time move with it. Replacing the session sits below a rule and asks once, since it rewrites every block.

Behaviour

The chips arrive late, and that is fine

The week payload has none of these fields — they only exist on GET /schedule/trainings/{id}. So the card paints title, blocks and shape bar from the week data immediately, and the rail fades in when the detail lands. Reserve its height (one chip row, 26 px) so nothing below jumps. The shoe list is lazier still: GET /me/shoes fires the first time the shoe editor opens.

Responses replace state, they don’t patch it

All seven mutations hand back the complete ScheduledTrainingDetail. So a commit swaps the whole training object — never merge a field by hand. It matters: changing intensity rewrites every block’s pace, its hex_graph, and the totals, and it can flip other capability flags. The rail is a pure projection of the last response.

Pending on the chip, not over the card

A commit swaps the chip’s icon for a spinner and leaves everything else usable. No overlay, no disabled card. A second commit while one is in flight is refused with a short message rather than queued — these calls all rewrite the same object, so overlapping them races the response.

Failure keeps the old value visible

Nothing is applied optimistically. The chip shows the last server truth until a response arrives, so a failed call needs no rollback — just a toast that names what didn’t happen: “Couldn’t change the shoe. Tap to retry.” The one exception is the numbers in the identity strip, which flash once when they change so a rescale is not silent.

Spilling the colour into the month grid

optional, one line of CSS

Today a scheduled day gets a generic blue dot. Since hex_training is already per-workout-type, painting the dot with it turns the month into a training-mix overview: three oranges in a week is a lot of tempo. Completed keeps its green, missed keeps its red — status still beats type. It only works because the dot never carries meaning alone; the day’s session name is one tap away, and the legend below is worth showing once.

Open questions

blocks marked ! need an answer before build
!

Two capabilities arrive with no way to act on them

can_change_pacing_plan ships a full change_pacing_plan_package, and can_toggle_cooldown / has_cooldown ship as a pair — but training.ts has no setter for either, and neither endpoint has been observed. Both are false on every payload captured so far, so the design reserves a row for each and ships neither until we can watch the app send one.

!

Nothing tells us which activities a session can become

CROSS_TYPES holds exactly one value, road_bike, and there is no endpoint listing what can_cross_train would accept. The activity picker can therefore only offer Run and Cycling. If the mobile app shows more — swim, elliptical, hike — the list comes from somewhere we haven’t found. Worth a capture session before this row ships.

!

We can’t tell the coach’s shoe from the runner’s shoe

suggested_shoe is one field doing two jobs: it is the recommendation and the assignment, so after the first change the recommendation is gone. The design sidesteps it by badging preferred shoes as “Favourite” instead of labelling anything “Recommended”. If the backend can add a suggested_by or keep the original id, the sheet can offer “back to the suggested pair” — which is the thing a runner will actually ask for.

?

Is an exchange reversible?

Cross-training is documented as revertible by exchanging the training. Whether the original workout stays in the candidate list after an exchange is unknown. It decides the confirm copy: “Replace” if it can be undone, “This can’t be undone” if not. Cheap to answer — exchange once and re-read the candidates.

?

Elevation as a number

training_condition accepts height_value and height_unit alongside the four presets. The prototype posts the presets only, with height_value: 0. If the presets turn out to be derived from the number server-side, the tiles are lying and we need a metres field instead. Until then, four tiles beat a numeric input on a phone.

?

Titles are localised, colours are not

title comes back in the user’s language, so nothing may key off it — no “if the title contains tempo” icon mapping. hex_training is stable and shared with the mobile app, which is why it carries the type coding here. The unresolved half: whether those hues are a fixed palette per workout type or per training plan. If they drift, the calendar legend can’t be static.

Build order

svelte 5 runes, matching the existing calendar components

New pieces

  • session-identity.svelte — accent rail, activity icon, title, live totals, shape bar.
  • session-shape-bar.svelte — flattens training.blocks (group blocks × repeat) into weighted segments coloured by hex_graph.
  • setup-rail.svelte — the chips; pure function of the detail object.
  • session-setup-sheet.svelte — the two-level <dialog>, matching change-date-modal.svelte’s pattern.
  • session-detail.svelte.ts — one store per selected training: fetch on select, mutate, replace wholesale, expose pending.

Endpoints to add

  • GET /api/v1/training/[id] — the detail, and the only source of the flags.
  • POST /api/v1/training/[id]/condition
  • PUT /api/v1/training/[id]/intensity, /distance, /shoe, /cross-train
  • GET + PUT /api/v1/training/[id]/exchange
  • GET /api/v1/shoes — lazy, cached for the session.

Every one is a thin pass-through to the already-written trainingApi, guarded the same way training/delete is.

Order

  • 1 · Read. Detail fetch, identity strip, shape bar, chips rendering current values. No editing. Ships value on its own — right now the runner can’t see the shoe or terrain at all.
  • 2 · Tune. Effort, volume, terrain, shoe. All four are the same commit path, so they land together.
  • 3 · Replace. Activity and workout swap, behind the confirm. Last because it needs the open questions answered.

Deliberately not in this design

  • Per-block editing. The API only takes whole-session percentage steps; a block-level editor would imply a precision the endpoint doesn’t have.
  • A free distance field. distance_value is a percentage delta capped by the coach, not a distance. Only the server’s steps are offerable.
  • A workout-type icon set. Localised titles and an open-ended type list make it guesswork; colour and shape bar carry it instead.
  • Settings in the month grid. Editing stays in the detail card — the grid gets colour only.
