UX design · training session settings

The session card reads its own permissions.

Five new endpoints let a runner reshape a planned session: terrain, effort, volume, shoe, and the session itself. This design puts all of it behind one row of chips that doubles as the status display — what is applied is what you tap to change.

The hard question was “which change is allowed on which workout?” It turns out we never have to answer it. GET /schedule/trainings/{id} ships can_change_distance, can_change_intensity, can_cross_train, can_be_exchanged and the matching change_*_package objects — steps, labels and coach copy included. The UI is a projection of that response. A tempo run that refuses a distance change simply arrives without the chip.

Identity strip

Colour comes from the server, not from us

hex_training is already per-workout-type — #E69F00 for tempo, #7B3294 for easy + strides, #1BB9AA for cycling — and it is the same value the mobile app paints. We use it for the 3 px rail and an 18% tint behind the activity icon, never as text colour: several of those hues fail contrast on the charcoal ground.

Identity strip

The icon says the activity, the bar says the shape

One icon per activity (run, bike) is safe to derive from cross_type. A second icon set for workout type would not be: titles are localised and the list is open-ended. Instead the 6 px shape bar draws the blocks — a solid slab is a tempo, a comb of thin marks is intervals or strides. It costs one line and reads before the title does.

Chip rail

The badge is the button

Every chip is both the applied value and the way in. Chips that still match the coach’s plan sit muted; anything you changed picks up a pink dot and a tinted border, so “what did I touch on this session” is one glance.

Chip rail

The rail and the index are one list

Both render from the same array of settings, so a setting cannot carry a different name, icon, value or position in one than it has in the other — “Adidas Boston 13” on the chip is “Adidas Boston 13” in the row. What differs is only which ones show: terrain and shoe always, because they are the session’s standing setup; effort, volume and cool-down only once they differ from plan, since at “as planned” they are noise. Activity and workout never get a chip — the identity strip is already showing them, the icon for one and the title for the other.

Chip rail

One trailing control, not a toolbar

The sliders chip is the only always-present affordance and the only way to reach a setting that has no chip yet. The header keeps the icons it already has — treadmill mode, move date, delete — because those act on the session as a whole rather than on its setup. Treadmill mode stays mobile-only as it is today, and now also drops off a cross-trained session: a ride has no pace to hold, so it goes with the rest of the running detail.

Sheet

Two levels, one screen deep

A chip opens the sheet directly on its editor; the sliders chip opens the index and you drill in once. A pick commits and closes — shoe, activity, workout. A dial commits and stays, because the whole point of moving the effort step is watching the total time move with it. A switch commits in place.

Sheet

One question, however many endpoints answer it

“Make this session something else” is one thing a runner wants. The API splits it in two: cross_train takes an activity, exchange takes a candidate id, and they overlap at the edges — exchange candidates can themselves be cross-trained, and reverting a ride is a cross-train with no type. Offering that as two rows makes the runner guess which list holds the answer, to no benefit: the split is ours to absorb.

So it is one list, grouped by what each option is — another session, or a different sport — rather than by which call serves it. Which endpoint fires is decided per option, at the moment of tapping. When only one of the two flags is set only that group renders.

And it opens from the title. The chips put terrain and shoe on the card while the biggest change of all sat two taps deep behind the sliders button, which is exactly backwards. The title is the session’s badge, so by the same rule the chips follow it is also the way to change it — a small swap glyph beside it, no new chrome. The title stays a plain heading on a session that cannot be replaced.

Sheet

Reversible means no confirm dialog

Swapping the workout or the activity rewrites every block, but it can be swapped back — so it doesn’t deserve an “are you sure”. Tap the alternative, it commits, and the card holds an Undo for eight seconds. One tap to change, one tap to change back, no modal in between.

The two halves undo differently, and the offer is honest about it. A cross-train’s inverse is exactly a cross-train, so that one is precise. An exchange has to exchange back, which needs the old session to still be among the candidates — so the list is refetched first and the Undo appears only once that candidate is in hand. Promising one that would fail on the tap would be worse than not offering it.

Shoe

One label, then the server’s order

The recommendation is the server’s, so it is labelled Recommended and pinned to the top. Below it the shoes stay in the order the API sent them — stable, and never re-sorted by anything we invented. Each row carries its type and its wear, so a pair at 79% is visible before you pick it, and retired pairs are filtered out because they are not a choice. That keeps the rule that holds everywhere else in this design intact: the server decides, we render.

Cool-down

The control sits on the block, not in a settings list

Every other setting is session-wide, so it belongs in the sheet. The cool-down is not — it acts on one block, and that block is already on screen. So the control is a Remove on the cool-down row itself, and once removed the row stays as a dashed ghost: the plan shows what is missing and offers it straight back. Nothing is buried a tap deeper than the thing it changes.

Flipping it moves everything at once — the block, the shape bar’s trailing segment, and the totals. Seeing the plan change is the confirmation, so there is no dialog. The sheet index still lists it, because the index is the full inventory of what this session allows, but nobody has to go there for it.

The whole row is the control, not a button parked at the end of one — a bigger target, and obviously interactive. Both states carry the same bordered action, so neither hides; the accent sits on that action alone when the cool-down is gone. Enough to find, without a whole pink row shouting about a block the runner removed on purpose. It used to have a “No cool-down” chip as well, which spent a row of the rail repeating what the plan says in the very place the block is missing from.

Behaviour

The chips arrive late, and that is fine

The week payload has none of these fields — they only exist on GET /schedule/trainings/{id}. So the card paints title, blocks and shape bar from the week data immediately, and the rail fades in when the detail lands. Reserve its height (one chip row, 26 px) so nothing below jumps. The shoe list is lazier still: GET /me/shoes fires the first time the shoe editor opens.

Responses replace state, they don’t patch it

All seven mutations hand back the complete ScheduledTrainingDetail. So a commit swaps the whole training object — never merge a field by hand. It matters: changing intensity rewrites every block’s pace, its hex_graph, and the totals, and it can flip other capability flags. The rail is a pure projection of the last response.

And it goes further than the card. The week the calendar holds is a separate copy of the same training, so a change that stops at the detail leaves the card right and everything around it a version behind — the old distance in the grid, the old colour on the dot. Each response is handed back to the calendar store, which swaps that one training and updates its month cache alongside, since the cache holds the very object it serves. No refetch: the response already is the new week’s worth of that session.

Pending on the chip, not over the card

A commit swaps the chip’s icon for a spinner and leaves everything else usable. No overlay, no disabled card. A second commit while one is in flight is refused with a short message rather than queued — these calls all rewrite the same object, so overlapping them races the response.

Failure keeps the old value visible

Nothing is applied optimistically. The chip shows the last server truth until a response arrives, so a failed call needs no rollback — just a toast that names what didn’t happen: “Couldn’t change the shoe. Tap to retry.” The one exception is the numbers in the identity strip, which flash once when they change so a rescale is not silent.

Spilling the colour into the month grid

revised — strength needs shape, not colour

Today the grid has exactly three dot colours, and running and strength share all three: calendar-cell.svelte paints both dots from --color-dot-scheduled, --color-dot-completed and --color-dot-missed. Strength has no colour of its own. The only thing separating the two is that the strength dot sits second in the pair — which works on a day that has both, and tells you nothing on a day that has only strength.

That breaks the idea of painting the run dot with hex_training: the moment one dot carries workout type, the two stop being parallel and the pair reads as one coloured thing next to one blue thing. So the rule has to split — shape says what it is, colour says how it is going. A run stays a filled dot, strength becomes a small bar. Then the run dot is free to carry its training colour while scheduled, and completed green and missed red still override it, because status beats type.

Open questions

blocks marked ! need an answer before build
?

Resolved: the cool-down request names its field differently

The path was right — PUT /schedule/trainings/{id}/cooldown — but the body key is cooldown_toggle, not has_cooldown. It is the only mutation whose request field is named differently from the field it sets, and the wrong key is not rejected: the call is answered 200 with the training unchanged. That failure mode is why the toggle is checked against the response rather than trusted, and why setup errors now surface on the card instead of only inside the sheet.

!

A change package's value means different things on different sessions

change_distance_package sends percentage deltas on a steady run — -5 for “-5%”, with a 0 step meaning “as planned”. On an interval session the same package counts repetitions: 1, 2, 3 for “1x”, “2x”, “3x”, titled “Fine-tune intervals”, and with no zero step at all.

That breaks the obvious test for “has the runner changed this”. Comparing against 0 marks an untouched interval session as changed, because 2x is not zero. So the rule is: a package with a zero step can say what deviates from the plan and its chip appears only when it does; a package without one cannot, so its value is shown plainly and always. Nothing may do arithmetic on a step's value either — pass it back, render its text.

?

Resolved: terrain writes the whole condition, in labels

Both enums travel as the labels the read side returns — height_difference: "flat", surface: "treadmill" — and all four fields go up on every call. This is the one write that does not merge a partial body: a field left out is answered “The height difference field is required” rather than kept at its stored value, so a runner changing only the surface still carries the height, which defaults to 0 metres.

An unrecognised label is refused with “The selected height difference is invalid”, which is why the terrain editor stages a known value rather than passing an unfamiliar one through — a session carrying an elevation the app does not know would otherwise fail on a field the runner never touched.

Altitude is a field under the two tile rows: metres of ascent, optional, 0 by default. It joins the terrain chip only once it is set — every session without one would otherwise carry a “0 m” nobody asked about.

The labels are the app’s own words rather than the API’s: flat, slightly hilly, very hilly, mountainous for a scale whose values read flat, lights, strong, mountain. Each carries the threshold it stands for — under 3, 3–10, 11–20, over 20 metres of ascent per kilometre — which is what turns four vague words into something a runner can check a route against. Enter an altitude and the field says what it works out to per kilometre, and which band that reads as. It never changes the selection: a session can average 4 m/km and still be one brutal climb. And single_track is labelled “Single track”, not “Trail”: it is a trail, but a narrow one, and the app also offers a wide unpaved road — the difference between those two is the whole point of asking.

!

The surface values are not the surface names

All five surfaces are offered — road, athletics track, treadmill, dirt road, single track — but two of them travel under a name the app never shows. A track posts as track; athletics_track, which is what the app’s own label reads like, is answered “The selected surface is invalid”. An unpaved road posts as dirt_road. Both values were captured by setting the surface in Trenara’s app and reading what came back, which is the only way to learn one: the terrain call carries the elevation and climb, so a guessed surface also loses a change the runner did make. A surface we have never seen still reads correctly, under its own humanised name — which is how these two were caught.

?

The applied setting lives in the package, not in the condition

training_condition comes back null on a training whose terrain has never been set — even when a distance step is applied and an intensity step is selected. So training_condition.intensity is not where the current effort lives; the selected flag on the package's steps is. A card reading the condition would show nothing on exactly the sessions a runner has been adjusting.

?

Which block is the cool-down?

Nothing in the payload flags it, so the control finds it by matching a block type containing “cool” — the same assumption blockTypeColor already makes. A session can report has_cooldown while naming its block something else, and attaching the control to the wrong block would be worse than not finding one, so the fallback is a row of its own rather than a guess. A block-level flag upstream would remove the guesswork entirely.

?

Resolved: all seven activities are now captured

The guesswork is gone. Alongside road_bike (Cycling), the API takes mountain_bike, indoor_cycling, swimming, crosstrainer and elliptical — the near-synonyms that made guessing risky, cross trainer and elliptical bike, turned out to be crosstrainer and elliptical respectively, one word apart from each other and from nothing an educated guess would have landed on. All six now sit in the picker alongside Run, in the app's own order.

“Keep as a run” is confirmed too: reverting a cross-train sends { cross_type: null } to the same cross_train endpoint, never an exchange. And a session already cross-trained to an unregistered type still reads correctly regardless — the label registry was always a display convenience, not a whitelist, so an eighth activity added upstream shows its humanised name instead of breaking.

?

Resolved: the pacing plan is three radio buttons, not a dial

Captured off the goal race itself. PUT /schedule/trainings/{id}/pacing_plan takes { pacing_plan: "trenara" | "alternative" | null } and hands back the whole training, same as every other mutation here. And change_pacing_plan_package confirmed the shape the design notes predicted: it is not a ChangePackage at all — no wrapping title/text, the field is itself the array of three options, each with its own order, value, title, description and selected:

1 "trenara" "Pacing plan" "All roads lead to Rome, but this is my preferred pacing plan for your race." 2 "alternative" "Plan B" "Always have a plan B in place. Sometimes plan A doesn't match how you feel or the race-day circumstances. Here's an alternative pacing plan." 3 null "No pacing plan" "One block at your selected pace."

Confirms the design call too: this is a picker, not a step scale. That is also literally how the app itself shows it — three radio buttons in the session view for that training, each with the coach's own copy under it, and no separate confirm step. So it is radio buttons here as well, and real ones: one choice from a fixed set with exactly one applied is what a radio group is, and it brings the keyboard and screen-reader behaviour that a row of pressed-state buttons has to imitate. No option is treated as “the plan”, since nothing in the payload marks one as the coach's default over the runner's last choice — so unlike effort or volume, picking a strategy is never flagged as a deviation, only shown as what is set.

It does not go behind a chip. Three strategies that only mean anything alongside a paragraph of the coach's copy do not compress into a pill, and race day is the emptiest card in the plan — everything else on it is pinned. So the group sits on the card, directly under the blocks it rewrites, exactly as the cool-down control sits on its own block: the control belongs where the thing it changes is already on screen. The sheet still lists it, because the index claims to be the full inventory of what a session allows, and that claim has to survive race day.

?

Resolved: can_be_edited is not a master switch

Race day showed nothing at all — no chips, no rail, no pacing plan — and the cause was one line: canShowSetup required can_be_edited, so a single false hid the whole of setup. The goal race disproves that reading outright. It sends can_be_edited: false together with can_change_intensity: true and can_change_pacing_plan: true — the server saying, in the same payload, both “you may not edit this training” and “these two settings are open”. Read as a master switch it hid the pacing plan on the one session that has one.

Every setting is already gated on the flag that governs it, so the rail simply asks whether any setting survived. can_be_edited keeps the two jobs it can actually speak for: the delete and move-date controls, which are edits to the schedule entry, and terrain and shoe — the only two settings the API ships no can_* for, so it is the sole signal we have about them.

That last part is a judgement call, not a fact, and it is the open half of this. can_be_edited may well mean only “this entry cannot be moved or deleted”, in which case terrain and shoe are changeable on race day and hiding them costs a shoe recommendation the server bothered to compute — an ASICS Metaspeed Edge, on the one day it matters most. Showing them and letting the server refuse is the other defensible answer. It stays conservative until a capture settles it: one POST .../training_condition against the goal race is the whole experiment.

!

The recommendation is destroyed the first time you change it

suggested_shoe is one field doing two jobs — it is the recommendation and it is the assignment — so the moment the runner picks something else, what was recommended is gone. The whole shoe list now rests on that label, and there is no fallback: without the original id there is simply no Recommended row after the first change, and the list is an unordered locker. This is the one open question that blocks the shoe editor rather than merely limiting it. A second field, or a flag on the shoe, closes it; the prototype models it as suggestedShoeId.

?

Does swapping back restore the tuning?

The exchange itself is reversible, which is why the confirm dialog is gone and the Undo toast took its place. What the toast promises is still worth checking: swapping away and back rebuilds the blocks from the coach’s plan, so an effort or distance step set beforehand is probably lost. If it is, Undo should re-apply those two calls after the exchange rather than pretending one call undoes everything — and the toast should say “Swapped back” rather than implying nothing happened.

?

Elevation as a number

training_condition accepts height_value and height_unit alongside the four presets. The prototype posts the presets only, with height_value: 0. If the presets turn out to be derived from the number server-side, the tiles are lying and we need a metres field instead. Until then, four tiles beat a numeric input on a phone.

?

Titles are localised, colours are not

title comes back in the user’s language, so nothing may key off it — no “if the title contains tempo” icon mapping. hex_training is stable and shared with the mobile app, which is why it carries the type coding here. The unresolved half: whether those hues are a fixed palette per workout type or per training plan. If they drift, the calendar legend can’t be static.

Build order

svelte 5 runes, matching the existing calendar components

New pieces

  • session-identity.svelte — accent rail, activity icon, title, live totals, shape bar.
  • session-shape-bar.svelte — flattens training.blocks (group blocks × repeat) into weighted segments coloured by hex_graph.
  • setup-rail.svelte — the chips; pure function of the detail object.
  • session-setup-sheet.svelte — the two-level <dialog>, matching change-date-modal.svelte’s pattern.
  • session-detail.svelte.ts — one store per selected training: fetch on select, mutate, replace wholesale, expose pending.

Endpoints to add

  • GET /api/v1/training/[id] — the detail, and the only source of the flags.
  • POST /api/v1/training/[id]/condition
  • PUT /api/v1/training/[id]/intensity, /distance, /shoe, /cross-train
  • GET + PUT /api/v1/training/[id]/exchange
  • PUT /api/v1/training/[id]/cooldown — once we know the upstream path
  • GET /api/v1/shoes — lazy, cached for the session.

Every one is a thin pass-through to the already-written trainingApi, guarded the same way training/delete is.

Order

  • 1 · Read. Detail fetch, identity strip, shape bar, chips rendering current values. No editing. Ships value on its own — right now the runner can’t see the shoe or terrain at all.
  • 2 · Tune. Effort, volume, terrain, shoe. All four are the same commit path, so they land together.
  • 3 · Replace. Activity and workout swap with the Undo toast. Workout can ship as soon as the candidate list is wired; activity waits on the cross_type enumeration.
  • 4 · Cool-down. A control on the block plus a switch in the index. Small, but it is the one change that visibly rewrites the plan, so it wants the block list and shape bar from step 1 already in place.

Deliberately not in this design

  • Per-block editing. The API only takes whole-session percentage steps; a block-level editor would imply a precision the endpoint doesn’t have.
  • A free distance field. distance_value is a percentage delta capped by the coach, not a distance. Only the server’s steps are offerable.
  • A workout-type icon set. Localised titles and an open-ended type list make it guesswork; colour and shape bar carry it instead.
  • Settings in the month grid. Editing stays in the detail card — the grid gets colour only.
